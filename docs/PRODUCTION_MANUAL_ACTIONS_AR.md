# الإجراءات اليدوية المطلوبة لإطلاق AZKAR

الدليل ده فيه الإجراءات اللي محتاجة دخول صاحب المشروع للوحة GitHub أو
Cloudflare أو Supabase. ما تبعتش أي token أو مفتاح أو بيانات دخول في الشات.

## 1. مطلوب قبل تفعيل النشر

### Cloudflare — افصل Workers Build القديم

1. افتح **Cloudflare Dashboard → Workers & Pages → azkar-sadaqa →
   Settings → Builds**.
2. اختار **Disconnect** للـGit build الحالي، أو عطّل production builds لو
   اللوحة بتعرض الاختيار ده.
3. ما تحذفش الـWorker، وما تغيرش اسمه أو hostname.
4. السبب: الإعداد اللي اتفحص كان بيرفع ملفات `web/` المصدرية بدل
   `build/web`؛ تشغيله جنب GitHub Actions ممكن يعمل نشرين متنافسين.
5. التغيير يفصل البناء الآلي فقط وما ينشرش نسخة جديدة. بعد الحفظ، اتأكد إن
   Worker `azkar-sadaqa` ما زال موجوداً ورابطه كما هو.

### GitHub — اعمل بوابة موافقة production

1. افتح `MTFOODA/Azkar → Settings → Environments`.
2. أنشئ environment اسمه بالضبط `production`.
3. فعّل **Required reviewers** واختار حساب المراجع المسؤول. ما تعتمدش على
   environment من غير reviewer؛ من غير حماية ممكن يكمل النشر تلقائياً.
4. أضف القيم التالية في **Environment secrets**:

   | الاسم | القيمة ومصدرها | التصنيف |
   |---|---|---|
   | `CLOUDFLARE_ACCOUNT_ID` | Account ID من لوحة الحساب المالكة للـWorker | معرّف حساب |
   | `CLOUDFLARE_API_TOKEN` | Token جديد محدود بـ **Edit Cloudflare Workers** وعلى الحساب المطلوب فقط | حساس |
   | `AZKAR_SUPABASE_URL` | Project URL لمشروع Supabase الإنتاجي | عام |
   | `AZKAR_SUPABASE_PUBLISHABLE_KEY` | anon/publishable key من إعدادات API للمشروع | مفتاح عميل عام؛ سيظهر في JavaScript المبني |

5. من **Environment variables** أضف `AZKAR_AUTH_SCHEMA_VERIFIED=false`.
   لازم يفضل false لحين اجتياز اختبارات RLS الحية المعتمدة. الـworkflow
   هيفشل بأمان لو القيمة مش true بعد التحقق.
6. Cloudflare API Token مطلوب وقت deploy فقط. صلاحية Workers Scripts edit
   على الحساب المناسب كفاية لـ`workers.dev`؛ ما تضفش صلاحيات Zone أو DNS
   غير مطلوبة. لا تحفظه في repository files أو Logs.
7. المتوقع بعد الإعداد: التحليل والاختبارات يشتغلوا أولاً، وبعدها يطلب
   GitHub موافقة قبل build والنشر.

## 2. مطلوب قبل اختبار المصادقة الحية

### Supabase — عناوين الرجوع

1. افتح **Supabase Dashboard → Authentication → URL Configuration** للمشروع
   المستخدم للإنتاج.
2. اضبط **Site URL** إلى:

   `https://azkar-sadaqa.mohamed-fooda-mtf.workers.dev`

3. أضف إلى **Redirect URLs**:
   - `https://azkar-sadaqa.mohamed-fooda-mtf.workers.dev/dashboard`
   - `https://azkar-sadaqa.mohamed-fooda-mtf.workers.dev/reset-password`
4. احتفظ بكل روابط التطوير الموجودة؛ أضف الروابط دي من غير استبدال قائمة
   الروابط أو حذف مدخلات تانية.
5. التطبيق يطلب `/dashboard` بعد التسجيل وتأكيد البريد، و
   `/reset-password` بعد استعادة كلمة المرور. لا تضف callback route بالتخمين.
6. افتح **Authentication → Sign In / Providers → Email** وتأكد إن موفر
   البريد مفعّل وإن إعداد تأكيد البريد الحالي مقصود. ما تغيّرش سياسة التأكيد
   من غير مراجعة؛ سجّلها قبل اختبار التدفق.
7. المتوقع: رسالة التأكيد/الاستعادة ترجع للمسار المقصود على Worker. تحقق
   بتجربة معتمدة بعد النشر.

### Supabase — تفعيل حارس التسجيل

قبل تحويل `AZKAR_AUTH_SCHEMA_VERIFIED` إلى `true`:

- اتأكد إن المشروع الحي يحتوي provisioning trigger الموجود مسبقاً وإنه ينشئ
  صفحة واحدة لكل مستخدم.
- اختبر بحسابين معتمدين إن كل مالك لا يقرأ أو يعدل بيانات الآخر.
- اختبر إن الزائر المجهول يقرأ المنشور فقط ولا يكتب.
- اختبر إن الصفحة غير المنشورة ومحتواها غير متاحين للزائر.
- تحقق إن صلاحية الإدارة تعتمد على سجل إداري فعّال في قاعدة البيانات.

ما تشغّلش migration الأولية مرة أخرى على قاعدة موجودة، وما توقفش RLS. إنشاء
حسابات أو بيانات على production محتاج موافقة منفصلة. من غير الاختبارات الحية،
سيظل التسجيل محجوباً والـworkflow متوقفاً عن النشر.

## 3. مطلوب قبل الإطلاق العام

1. بعد رفع تغييرات الإعداد محلياً، راجع الملفات والاختبارات واطلب موافقة
   صريحة قبل دفع commit إلى `main`؛ الفرع متصل بنشر production.
2. بعد وصول workflow المعتمد إلى `main`، افتح
   **Actions → Deploy AZKAR Worker**. راجع commit ونتيجة `Analyze and test`.
3. وافق على GitHub environment `production` فقط بعد مراجعة اسم Worker
   `azkar-sadaqa` ومخرجات build. التأكيد ينشر إلى الرابط العام الحالي.
4. راجع سجل Wrangler في workflow؛ لازم يوضح نشر `build/web` للـWorker
   الموجود. سجل Build ID أو Version ID من Cloudflare.
5. في نافذة خاصة، اختبر homepage والروابط المباشرة وتحديث `/m/<slug>`، ثم
   اختبر الدخول والاستعادة والمشاركة على الحسابات المصرح بها.
6. لا تعتبر HTTP 200 وحده نجاحاً: اتأكد إن HTML فيه Flutter bootstrap
   المترجم وملفات JS/assets تُحمّل من غير أخطاء.
7. قبل فتح التسجيل العام، أكمل اختبارات RLS والحسابات المعتمدة وسجل النتيجة.
   لا تنشئ حسابات production تلقائياً.

## 4. اختبارات يدوية

### تسجيل ومشاركة صفحة

بعد موافقة صاحب المشروع على حساب اختبار:

1. افتح `/register`؛ لازم تظهر أربعة حقول فقط: الاسم والبريد وكلمة المرور
   وتأكيد كلمة المرور.
2. أنشئ حساب الاختبار، أكد البريد حسب إعداد Supabase، ثم سجل الدخول.
3. افتح لوحة التحكم ← إعدادات صفحتي، وعدّل العنوان والـslug؛ لا يوجد عنوان
   أو slug في نموذج التسجيل.
4. أضف محتوى اختبار غير حساس، وانشر الصفحة بعد التأكد من إعدادات الخصوصية.
5. انسخ الرابط. لازم يبدأ بـ
   `https://azkar-sadaqa.mohamed-fooda-mtf.workers.dev/m/` ولا يحتوي
   localhost أو `pages.dev`.
6. افتحه من نافذة خاصة أو هاتف آخر غير مسجل. تحقق من ظهور المحتوى المنشور
   فقط ومن عمل refresh.

### فحص الخصوصية

- افتح صفحة غير منشورة وأحد روابط محتواها كزائر مجهول؛ لازم ما يظهرش المحتوى.
- استخدم حسابي اختبار منفصلين بموافقة صاحب المشروع؛ المالك الأول لا يعدل صفحة
  المالك الثاني.
- افحص Supabase RLS من عميل مجهول؛ الكتابة لازم تترفض.
- لا تستخدم مفاتيح service-role أو مسؤول قاعدة البيانات في المتصفح.

## 5. اختياري لاحقاً

- ربط domain مملوك بعد تقييمه وتحديث Site URL وredirects و`PUBLIC_BASE_URL`
  في build-time.
- إضافة معاينات Open Graph ديناميكية لصفحات memorial بعد تصميم قراءة عامة
  آمنة واختبارات نشر/إلغاء نشر.
- اختبارات هاتف فعلي إضافية؛ علّمها غير مختبرة لو ما توفرش الجهاز.
